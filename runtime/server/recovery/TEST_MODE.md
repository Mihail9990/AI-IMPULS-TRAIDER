# RECOVERY: запуск только тестового режима

## Проверка без MT5, счёта и VPS
Из каталога `server` в Python-окружении с зависимостями проекта:

```sh
python -m unittest discover -s tests -v
python -m compileall -q recovery
```

Сквозной сценарий с фальшивым терминалом:

```sh
PYTHONPATH=tests:. python -m unittest test_recovery_service_loop -v
PYTHONPATH=tests:. python -m unittest test_recovery_close_api -v
```

Тесты проверяют первичное исполнение, защитный SL, повторный вход,
перенос встречного ордера, закрытие через API и подтверждённый P/L.
Они не свидетельствуют о работоспособности с настоящим брокером.

## Локальный API симуляции

```sh
export WIDGET_TOKEN="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"
export WIDGET_LIVE=0
python run_recovery_sim.py
```

API слушает только `127.0.0.1:8767`. Запросы требуют заголовок
`Authorization: Bearer <WIDGET_TOKEN>`. Не открывайте порт в интернет.
Этот runner использует простой симулятор, НЕ MT5 pipeline. Он не исполняет
реальные сделки и не реализует сквозное рыночное закрытие. Для телефона
потребуется отдельная безопасная доставка API; она здесь не настроена.

## Интегрированный API и последовательный сервис

Фабрика `create_mock_pipeline_app` принимает только MockPipeline с тестовым
MT5 double. Сначала создаётся MockService, он держится открытым всё время
работы API. Реальные MT5 модули отвергаются жёсткой проверкой transport.
Нельзя снимать проверку или подменять marker на настоящем модуле.

При старте сервис захватывает OS lock, перечитывает снимок Controller и
повторно проверяет привязку account/server/symbol/magic. Подтверждение
ранее отправленных outbox намерений использует только чтение broker snapshot,
без повторной отправки. Затем строится startup_report. Неизвестная экспозиция,
пропавшие ордера/позиции, несовпадение объёма или SL, PREPARED/неопределённые
намерения и ранее заблокированные диапазоны запрещают шаги сервиса и команды
API. GET состояния доступен владельцу для диагностики.

Это консервативная сверка, не автоматическое исправление: не догадка по
комментарию ордера, не отмена/закрытие неизвестного, не снятие blocked-флага.
После подтверждённого внешнего восстановления тестового состояния допускается
повторный evidence-only `service.reconcile_startup()`. Прямые низкоуровневые
helpers являются инструментами тестов, не безопасным публичным API.

При исследовании перезапуска сохраняйте ОБЕ базы: Controller и Executor.
Фальшивый терминал также должен сохранить своё состояние. Потеря outbox
не восстанавливается из одного Controller. Рекомендуется не запускать процессы
с отличающимися путями к одному файлу через hardlinks; Windows lock ещё не
проверен на целевом VPS.

## Что ещё блокирует промышленный запуск

- Настоящий терминал/Windows VPS, спецификация символа, tick/point и правила брокера.
- Проверка истории и раздельно поступающих комиссий, разрывов связи, рестартов.
- Решение пользователя по частичному входу после отмены остатка.
- Решение по классификации SL, когда начальная дистанция ровно 0.25.
- Полноценное восстановление неизвестных исходов и неоднозначных событий.
- Автозамена объёма pending при одновременно открытом другом диапазоне пока
  блокируется консервативно, а не исполняется по предположению.
- Реальное исполнение не подключено, не разрешено и не тестировалось.

Startup сверяет каждый сопоставленный pending с текущим логическим намерением:
идентичность ticket/scope/range/side, статус, тип BUY_STOP/SELL_STOP, точные
price/SL/TP/volume. Отсутствующее намерение или любое расхождение блокирует
продолжение, даже если исторический create intent ранее был VERIFIED.
Изменённые извне уровни не восстанавливаются автоматически.
Startup позиции также сверяются по scope, identifier, фазе binding,
соответствию entry/exit volumes фазе, направлению, средневзвешенному входу,
логической позиции и SL. Частичная позиция без logical state требует сохранённого
подтверждения SL на тот же наблюдаемый объём, иначе продолжение запрещено.
Это не полная сверка брокера: независимые комиссии и исторические пропуски
по-прежнему требуют дополнительного восстановления.

## Отдельный реальный адаптер: пока только read-only

`real_mt5_adapter.RealMT5ReadOnlyAdapter` не импортируется runner-ами и не
подключается автоматически. Принимает уже инициализированный MT5 API и явную
ожидаемую account/server привязку. Сам не вызывает initialize/login/shutdown,
не принимает пароль и не выбирает счёт. Читает bounded snapshot и проверяет
идентичность сессии до и после чтения. Требуется hedging account.

Это заготовка диагностической части реальной интеграции, НЕ работающий реальный
торговый исполнитель: preflight/send всегда запрещены; нет флага разблокировки;
MockPipeline её также отвергает. Проверки выполнены только на test doubles,
а не на реальном терминале. Смена счёта между двумя проверками туда и обратно,
согласованность нескольких read вызовов и полнота истории не гарантируются.
Следующий этап требует отдельно проверенного подключения на Windows VPS,
не торгового запуска этого файла. Уровни/тип ордера, торговые права, исполнения,
расхождения и recovery нужно проверить до проектирования разрешённого исполнения.

## Уточнение частичного входа
Пользователь выбрал оставить фактически открытую часть и отменить остаток.
MockService теперь защищает частичную экспозицию, запрашивает отмену остатка и
после VERIFIED отмены повторно сверяет фактический объём со сделками. Только
при совпадении принимается логическая позиция фактического объёма; исходный
заказанный объём сохраняется отдельно. Далее работают переносы SL и учёт
подтверждённого закрытия. Исполнение во время отмены или неопределённая отмена
не допускают принятия устаревшего объёма.

Объём следующего встречного/повторного триггера после неполного исполнения
ещё не выбран пользователем: `next_volume_policy_pending` запрещает генерацию
новых триггеров этого диапазона, но не блокирует управление SL текущей позиции.
Таким образом это не полная непрерывная RECOVERY-цепочка частичного входа.
Прежняя запись о необходимости выбрать оставить/закрыть частичную позицию
устарела; оставшаяся неопределённость относится к последующим объёмам.

### Последующее уточнение объёма после partial
Пользователь подтвердил: следующий триггер берёт объём из согласованной шкалы,
не из фактически частично открытой позиции. Принятая partial-позиция сохраняет
реальный объём; встречный ордер создаётся по следующему слоту полного SL.
После поддержки повторный вход использует текущий слот. На позиции слота24
встречного25-го ордера по-прежнему нет. Прежняя временная блокировка генерации
partial-триггеров удалена. Старые экспериментальные snapshots с уже подавленными
ордерами автоматически не достраиваются: пересоздайте тестовый сценарий, не
используйте такие snapshots для оценки восстановления на реальном счёте.

Partial acceptance дополнительно требует history poll ПОСЛЕ подтверждённой
отмены и повторную сверку ticket/identifier/scope/side/среднего входа/объёма.
IN+OUT с неизменным net volume, неизвестная история или расхождение entry
не принимаются как успешно управляемая partial-позиция. Такой диапазон
остаётся заблокирован для сверки. Bounded history всё ещё не доказывает
отсутствия отложенных/пропущенных брокером событий; live не разрешён.

## Native request gateway (заблокирован для реального исполнения)
Новый `mt5_execution_gateway.py` реализует отдельную границу MqlTradeRequest:
PENDING stop, SLTP, REMOVE и DEAL только для закрытия указанной позиции.
Проверяются поля/enum/числа, используется явная filling policy, при режиме
Market Execution цена DEAL исключается. Режим должен прийти из проверенной
спецификации брокера; здесь он не определяется автоматически.

Основание: официальные [order_send](https://www.mql5.com/en/docs/python_metatrader5/mt5ordersend_py)
и [order_check](https://www.mql5.com/en/docs/python_metatrader5/mt5ordercheck_py).
Успешная проверка не означает исполнения. Интерфейс check/send имеет
одноразовую проверку совпадающего запроса, сверку аккаунта и защиту от
повторной отправки после неопределённого исхода в пределах экземпляра.

Обычный constructor запрещает любые check/send до обращения к терминалу.
Только явно помеченный test double допускается через отдельную test factory.
Нет live unlock параметра. Это дополнительный низкоуровневый boundary, ещё
НЕ подключённый к durable Executor/MockService и НЕ замена их preflight:
тик/lot grid, stops/freeze, направление закрытия и принадлежность позиции
обязаны проверяться более высоким planner/transport слоем. Повторное создание
экземпляра не обеспечивает durable dedup; существующий Executor остаётся
обязательным при будущей интеграции. Реальное подключение не выполнялось.

### Gateway + durable Executor integration (test doubles only)
`GatewayTransport` теперь соединяет GuardedMT5Gateway с существующими
ownership/grid/quote проверками MT5Transport и durable Executor. Тестовая
конструкция: `Executor(GatewayTransport(fake, account=1, server='demo'), db_path)`.
Она не меняет default runner и отвергает real module. MT5 order_check считается
успешным только при retcode=0; TRADE_RETCODE_DONE не подменяет check success.
Проверены VERIFIED после отправки, отказ check, timeout UNKNOWN и запрет
повторной отправки после перезапуска durable outbox, смена аккаунта между
проверкой и send. Ветка Market Execution mapping остаётся standalone: этот
интеграционный transport использует текущую explicit-price модель planner;
автоматическая адаптация по broker execution mode ещё не реализована.

### Execution-mode adaptation и scope guard
GatewayTransport теперь читает `trade_exemode`/`filling_mode` перед check и
перед send. Market DEAL передаётся без price; остальные режимы сохраняют цену.
Pending требует RETURN независимо от execution mode. FOK/IOC для MARKET и
EXCHANGE допускаются только соответствующим symbol flag; REQUEST/INSTANT
не требуют флага. Политика не переключается автоматически. Неизвестные
метаданные или их изменение после check блокируют send.
Источник матрицы: [MQL5 Symbol Properties](https://www.mql5.com/en/docs/constants/environment_state/marketinfoconstants).

PENDING теперь требует явные expected symbol/magic и точное совпадение request
на обоих уровнях: Executor.prepare и MT5Transport.preflight. Это закрывает
отправку другого символа/magic под одобренным scope. Проверки остаются mock-only.

Scope guard расширен на все действия: любые присутствующие в request symbol
или magic должны точно совпадать с явным expected scope как в prepare, так и
в preflight. DEAL обязательно содержит оба поля. SLTP/REMOVE могут опускать
необязательные scope-поля, но не передавать иные; принадлежность ticket/position
по-прежнему проверяется отдельно по свежему snapshot. Negative tests покрывают
DEAL, SLTP и REMOVE до записи outbox и до отправки.
