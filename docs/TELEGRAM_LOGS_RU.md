# Диагностические TXT в Telegram (LIVE)

Опциональная исходящая отправка, без Telegram-команд и без доступа к торговому управлению.
Нужны собственный Telegram-бот и числовой ID **личного** чата с ним. Сначала пользователь
пишет боту `/start`. Группы намеренно не поддерживаются. Пользователь должен проверить,
что ID принадлежит его чату, прежде чем включать передачу диагностических данных.

## Настройка на VPS

В установщике основного бота нажать **«Настройки Telegram · логи .txt»**.
Введите токен от BotFather и числовой ID своего **личного** чата. Сначала напишите
боту `/start` и убедитесь, что ID относится к вашему чату. Включите отправку логов и сохраните. Автоматическая отправка выполняется каждые
10 минут; выключение этой настройки отключает и автоматическую, и ручную отправку. Пустое поле токена при последующем редактировании сохраняет
прежний токен. Кнопка «Отмена» ничего не меняет. Установщик требует остановить свой
процесс перед изменением; открытые позиции от остановки процесса не закрываются.
Сохранение настроек не отправляет тестовое сообщение и не запускает торговлю.
Изменения применяются при следующем запуске сервиса.

Токен и chat_id хранятся в отдельном `telegram-credentials.dpapi` рядом с runtime.log,
зашифрованными Windows DPAPI для текущего пользователя. Они НЕ записываются в
service.json, его резервные копии HTTPS-настройки, HTTP-ответы или диагностические TXT.
Токен скрыт в поле ввода и не заполняется повторно. Файл исключён из Git/релиза.
Обычная копия всей папки всё равно может содержать зашифрованный файл: это не переносимый
секрет и не замена резервному хранению у владельца. На новом VPS или под другим
пользователем Windows введите токен заново. DPAPI не защищает от программ, запущенных
под тем же Windows-пользователем. Не отправляйте токен в чат, логи или скриншоты.

Существующие переменные окружения процесса `AI_IMPULS_TELEGRAM_TOKEN` и
`AI_IMPULS_TELEGRAM_CHAT_ID` продолжают работать, пока локальные настройки не сохранены.
После сохранения локальный файл имеет приоритет, включая явное отключение отправки.
Повреждённый файл не вызывает тихий возврат к старому получателю из окружения.
Неполная/некорректная конфигурация показывает CONFIGURATION_ERROR и не мешает боту.
Сменить получателя уже существующей очереди нельзя: сначала нужно отдельно разобраться
с её доставкой, не удаляя недоставленные записи. Группы не поддерживаются.

Раз в 600 секунд отправляется TXT с новыми санитизированными контекстными записями:
изменения состояния и минутный heartbeat, фаза, цены/объёмы, результаты и настройки.
Это не все тики и не произвольный сырой журнал. Браузерные логи остаются только в браузере.
Пароли, токены, заголовки, счета, исходные комментарии/сообщения не отправляются;
идентификаторы проходят существующую диагностическую проекцию. Диагностика всё равно
содержит сведения о сделках. Telegram хранит документы в облачном чате бота, не в secret chat.

Отдельная очередь `<log_file>.telegram-outbox.sqlite3` хранит ещё не доставленные записи.
Только после Telegram `ok:true` + ID сообщения и совпадения chat_id отправленная часть
удаляется из очереди. Основной audit, SQLite торговли, RECOVERY и исходные логи сохраняются.
Пустой интервал не отправляется. Отказ Telegram сохраняет пакет до следующей попытки.
Обрыв с неизвестным результатом или сбой процесса после начала отправки даёт UNKNOWN:
автоповторы остановлены, потому что Telegram не предоставляет идемпотентный sendDocument.
Нельзя гарантировать exactly-once при потере ответа.

Пакет до 900 КБ. При накоплении более лимита отправляются последовательные части с шагом
10 минут, поэтому возможен backlog. Очередь до 50 МБ содержимого: старые недоставленные
записи не удаляются, новые сверх лимита не принимаются; счётчик потерь попадает в заголовок
следующих файлов. Сбой диска/аварийный выход может потерять записи ещё в общей RAM-очереди
диагностики (до 100 записей), при аварии это не обязательно отражается в счётчиках, которые тоже находятся в RAM.

## Ручная отправка из панели

В «Настройки → Логи» есть кнопка **«Отправить логи в Telegram .txt»**.
Она ставит отдельный диагностический запрос в постоянную очередь: не снимает SAFE_PAUSE,
не запускает цикл и не требует свежих котировок. Нельзя указать другого получателя через
браузер: используется тот же настроенный личный чат. Отправляются новые, уже записанные
в очередь санитизированные LIVE-записи (не произвольный файл и не браузерные логи).
При пустой очереди панель сообщает, что новых логов нет.

Отправляет один фоновый worker. Повторные клики/параллельные вкладки объединяются;
принятый request_id и результат сохраняются при перезапуске. При потере HTTP-ответа
браузер проверяет статус, не создаёт автоматически новую отправку. Если сервер не получил
запрос, можно явно повторить тот же request_id. Успех показывается только после
подтверждения Telegram; при неопределённости повтор заблокирован до сверки.
Статус доступен отдельной кнопкой «Проверить статус Telegram».

После ручной доставки следующий автоматический интервал начинается через 600 секунд.
Отправляется максимум один пакет 900 КБ; остаток остаётся в очереди для следующей отправки.
История идемпотентности ограничена 10 000 ручных запросов: при заполнении новые запросы
отклоняются, старые идентификаторы не забываются. Автоматическая отправка продолжает работать.
Запросы и подтверждения относятся только к диагностике, не к торговым командам.

## Проверка состояния и неопределённой доставки

Статус включён в начало диагностического TXT/просмотра логов и доступен через `TelegramLogs.status()` (READY/RETRY/UNKNOWN, очередь, потери,
batch и последний message_id). В браузере токен и получатель недоступны; настройки находятся только в локальном установщике. Для локальной диагностики
можно открыть отдельную очередь SQLite **только на чтение**, не торговую базу.
При UNKNOWN сначала найти в Telegram файл `live-logs-<batch>.txt`.
После остановки сервиса оператор может через локальный Python открыть `from_settings(log_file)`
и вызвать `resolve_unknown(batch, received=True)` только если файл действительно получен.
`received=False` разрешает повтор, который может дать дубль. Нельзя менять статус SQL вручную.
Нужен точный batch; изменение назначения при существующей очереди запрещено.
На одном outbox допускается только один процесс. Отправка работает, пока запущен основной
сервис; закрытие браузера не мешает, выключение VPS останавливает отправку.

Тесты используют подставной транспорт: настоящая доставка, Windows DPAPI и экран установщика требуют отдельной
проверки на VPS после настройки. По умолчанию ничего не отправлено и не включено.

## Причины SAFE_PAUSE и сверка

Экспорт включает последние диагностические коды проверки снимка и копию диагностики
при входе в паузу: например `TERMINAL_OBLIGATION_EVIDENCE_CHANGED` и статус обязательства
`EXTERNAL_EXIT`, `CLOSED_EVIDENCE`, `PARTIAL_CLOSE`. Идентификаторы хэшируются.
Известные причины отображаются как фиксированные коды; неизвестный текст не передаётся
(`OTHER_VALIDATION_FAILURE`/`OTHER_PAUSE_REASON`). Торговая сверка не меняется.
Старую причину паузы до обновления восстановить нельзя. Привязка причины к паузе находится
в памяти процесса; уже записанные в очередь диагностические записи переживают перезапуск.
