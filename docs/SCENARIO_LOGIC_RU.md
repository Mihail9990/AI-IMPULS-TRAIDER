# Фактическая логика сценариев 1–9

Этот документ описывает именно текущий код и помогает различать цены, которые
одновременно показываются в Telegram.

## Обозначения и формулы

Для примеров используются:

```text
STOP_DISTANCE = 1.00
TARGET_PROFIT = 0.30
POSITION_SIZE = 0.1
MAX_SCENARIOS = 9
```

У каждой стороны есть две разные цены:

* `original_trigger_level` — фактический первоначальный вход стороны; постоянен весь цикл;
* `current_entry` — фактический текущий вход; меняется после повторного открытия.

Защита считается от текущего входа:

```text
SL_LONG  = CURRENT_ENTRY_LONG  - STOP_DISTANCE
SL_SHORT = CURRENT_ENTRY_SHORT + STOP_DISTANCE

TP_LONG  = CURRENT_SL_SHORT + RECOVERY
TP_SHORT = CURRENT_SL_LONG  - RECOVERY
```

TP находится за SL противоположной позиции. Первоначальный спред и все виды
проскальзывания являются абсолютными расстояниями:

```text
INITIAL_SPREAD    = |LONG_FILL - SHORT_FILL|
SL_SLIPPAGE      = |PLANNED_SL - ACTUAL_SL_FILL|
TRIGGER_SLIPPAGE = |ORIGINAL_TRIGGER_LEVEL - ACTUAL_REOPEN_FILL|
```

Выгодное отклонение не превращается в ноль: получившееся расстояние полностью
участвует в `RECOVERY`.

## Когда меняется сценарий

**Stop Loss не увеличивает номер сценария.** Порядок такой:

1. Capital.com подтверждает закрытие стороны с `source=SL`.
2. Бот учитывает фактическую цену и SL slippage.
3. Бот пересчитывает TP оставшейся стороны.
4. Бот ставит trigger закрытой стороны на её `original_trigger_level`.
5. Если оставшаяся сторона достигает TP, цикл заканчивается.
6. Только подтверждённое исполнение trigger увеличивает `scenario` на один.

Математический переход находится в `Strategy.reopened()` в `trader/engine.py`.
Его вызывают обработчики trigger-fill в `trader/app.py`.

Working trigger создаётся сразу с предварительными SL/TP будущей позиции. Это защита
на случай мгновенного исполнения ордера, а не нарушение порядка SL → trigger.

## Почему SL может выглядеть близким к trigger

Это уровни разных объектов:

* SL относится к текущей открытой позиции и её `current_entry`;
* trigger относится к закрытой стороне и её первоначальному входу.

При `STOP_DISTANCE=1` проверять следует:

```text
|CURRENT_ENTRY_LONG  - SL_LONG|  = 1
|CURRENT_ENTRY_SHORT - SL_SHORT| = 1
```

Расстояние между SL одной стороны и trigger другой стороны не обязано быть равно
единице. Из-за спреда и повторных fills они могут находиться рядом. Кроме того,
Telegram может последовательно показать плановый SL старой позиции и trigger новой
позиции; проверить, к чему относится цена, позволяют `dealId` и `workingOrderId`.

## Сценарий 1

Фактические входы:

```text
LONG  = 4010.30
SHORT = 4010.00
SPREAD = |4010.30 - 4010.00| = 0.30
RECOVERY = 0.30 + 0.30 = 0.60
```

Уровни:

```text
SL_LONG  = 4010.30 - 1.00 = 4009.30
SL_SHORT = 4010.00 + 1.00 = 4011.00
TP_LONG  = 4011.00 + 0.60 = 4011.60
TP_SHORT = 4009.30 - 0.60 = 4008.70
```

Бот сначала подтверждает SL обеих позиций, затем подтверждает TP активных позиций.
Если позиция исчезла во время установки защиты, причина ищется в
`/history/activity`, а не выводится только из пустого `/positions`.

Пусть SHORT закрылся по `4011.08`:

```text
SL slippage   = |4011.00 - 4011.08| = 0.08
RECOVERY      = 0.60 + 0.08 = 0.68
Новый TP_LONG = 4011.00 + 0.68 = 4011.68
TRIGGER_SHORT = 4010.00
```

Номер всё ещё `1`. LONG по TP завершит цикл; исполнение SHORT trigger начнёт
сценарий 2.

## Сценарий 2

Пусть SHORT trigger `4010.00` исполнен по `4009.90`:

```text
TRIGGER_SLIPPAGE = |4010.00 - 4009.90| = 0.10
RECOVERY_2 = 0.68 + 1.00 + 0.10 = 1.78
SCENARIO = 2

SL_SHORT = 4009.90 + 1.00 = 4010.90
SL_LONG  = 4009.30
TP_LONG  = 4010.90 + 1.78 = 4012.68
TP_SHORT = 4009.30 - 1.78 = 4007.52
```

Если LONG затем закрылся по `4009.22`:

```text
SL slippage = |4009.30 - 4009.22| = 0.08
RECOVERY = 1.78 + 0.08 = 1.86
TP_SHORT = 4009.30 - 1.86 = 4007.44
TRIGGER_LONG = 4010.30
```

Номер остаётся `2` до исполнения LONG trigger.

## Сценарии 3–8

Каждый переход использует одни формулы:

```text
При trigger fill:
SCENARIO_NEW = SCENARIO_PREVIOUS + 1
RECOVERY_NEW = RECOVERY_PREVIOUS
             + STOP_DISTANCE
             + |TRIGGER_LEVEL - ACTUAL_TRIGGER_FILL|

При SL:
RECOVERY_NEW = RECOVERY_PREVIOUS
             + |PLANNED_SL - ACTUAL_SL_FILL|
```

После trigger fill рассчитываются SL повторно открытой позиции и TP обеих сторон.
После SL пересчитывается TP surviving-позиции и создаётся trigger закрытой стороны.

Если первым закрылся SHORT, переоткрытия чередуются так:

```text
2 SHORT, 3 LONG, 4 SHORT, 5 LONG,
6 SHORT, 7 LONG, 8 SHORT, 9 LONG.
```

Если первым закрылся LONG, порядок зеркальный. В сценариях 1–8 TP surviving-позиции
завершает цикл и отменяет относящийся к нему trigger. При `/stop` следующий цикл ждёт
`/start`; без паузы бот возвращается к свечному фильтру.

## Сценарий 9

Сценарий 9 начинается после trigger-fill из сценария 8. Ручной режим штатно не
включается. Бот:

1. сохраняет реализованные убытки сценариев 1–8;
2. отменяет working orders;
3. снимает SL/TP обеих позиций;
4. максимально параллельно закрывает LONG и SHORT по рынку;
5. использует фактические fills закрытия;
6. завершает цикл и возвращается к обычной автоматике.

```text
CLOSE_GAP = |ACTUAL_LONG_CLOSE - ACTUAL_SHORT_CLOSE|
TOTAL_LOSS_9 = REALIZED_LOSSES_1_8 + CLOSE_GAP
```

Пример:

```text
Убытки 1–8 = 20.00
LONG close = 4001.50
SHORT close = 4000.30
CLOSE_GAP = 1.20
TOTAL_LOSS_9 = 21.20
```

Если одна сторона успела закрыться по SL/TP во время снятия защиты, её fill берётся
из history, а оставшаяся позиция закрывается максимально быстро.

## Profit target следующих 200 циклов

```text
/profit200 0.4
```

устанавливает **полный** личный profit target `0.4` для следующих 200 завершённых
циклов. Текущий активный цикл не меняется. После 200-го завершения бот возвращается к
обычному `TARGET_PROFIT` из конфигурации.

## Синхронизация с Capital.com

Отсутствие позиции в `/positions` не считается самостоятельным доказательством SL
или TP. Причина берётся из `/history/activity`:

```text
source=SL → Stop Loss
source=TP → Take Profit
workingOrderId → связь нового входа с trigger
```

Если позиция открылась и закрылась между двумя REST-опросами, бот восстанавливает
цепочку из history и применяет события в порядке trigger fill → SL/TP → следующий
trigger либо завершение.

## Карта реализации

* `trader/engine.py: Strategy.stopped()` — SL, slippage и TP survivor; сценарий не меняет;
* `trader/engine.py: Strategy.reopened()` — увеличение сценария и recovery после trigger;
* `trader/app.py: _tick_cycle()` — основной контроль текущей фазы и классификация SL/TP;
* `trader/app.py: _create_trigger()` — trigger после подтверждённого SL;
* `trader/app.py: _detect_trigger_fill()` — обычное обнаружение исполнения trigger;
* `trader/app.py: _open_passed_trigger_at_market()` — MARKET fallback пройденного trigger;
* `trader/app.py: _recover_trigger_fill_then_stop()` и
  `_recover_trigger_round_trip_from_activity()` — быстрые события между REST-опросами;
* `trader/engine.py: complete()` — завершение по TP;
* `trader/engine.py: complete_scenario_nine()` — итог автоматического сценария 9.

Для проверки конкретного перехода в Telegram нужны: сторона и `dealId` закрытого SL,
его плановый и фактический уровни, `original_trigger_level`, `workingOrderId`,
фактический trigger fill, recovery до/после и новый номер сценария.

## Порядок Telegram-уведомлений

Telegram показывает действия в том порядке, в котором бот поставил сообщения в очередь.
Правильная последовательность после закрытия стороны теперь совпадает с брокерской хронологией:

1. `🛑 Stop Loss исполнен` — Capital.com уже подтвердил `source=SL`. Номер сценария ещё не
   меняется. В сообщении показаны плановый SL, фактическое закрытие, абсолютное slippage,
   recovery и сохранённый уровень будущего trigger.
2. `🛡 Защита подтверждена` — бот обновил и прочитал обратно TP surviving-позиции.
3. `📌 Trigger установлен` — working STOP принят на первоначальной точке входа закрытой стороны.
   `Projected SL/TP` относятся к будущей позиции, которая появится только после trigger fill.
4. `🔄 Trigger исполнен — переход в сценарий N` — trigger действительно открыл позицию;
   только здесь номер сценария увеличивается. Показываются фактический вход и trigger slippage.
5. Два сообщения `🛡 Защита подтверждена` — SL/TP обеих фактически открытых сторон прочитаны
   обратно из Capital.com для нового сценария.

На примере журнала 26 августа в сценарии 2 BUY уже закрылся по SL `4620.91`. Затем бот поставил
BUY trigger на постоянный уровень `4622.30` с проектируемым SL `4620.80`. Это два разных объекта:
`4620.91` — закрытие предыдущей BUY-позиции, а `4620.80` — будущий SL новой BUY после исполнения
trigger. Trigger исполнился позднее по `4622.30`, создал новый `dealId` и только тогда начался
сценарий 3. В прежней версии сообщение `📌 Trigger установлен` попадало в очередь раньше сообщения
о уже обработанном SL, из-за чего визуально казалось, что SL сработал после trigger. Торговая
последовательность была правильной; теперь исправлен и порядок сообщений.
