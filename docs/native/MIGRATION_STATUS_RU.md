## Архитектура

- `ImpulsTrader.mq5` + `NativeEngine.mqh` + `NativeControl.mqh` — единственный
  отправитель `OrderSend`. Закрытые M1, постановка и отмена STOP, корзины,
  подтверждение позиций, RECOVERY, TP, SL, CLOSE и независимые команды.
- `ImpulsObserver.mq5` — периодическая сверка через `HistorySelectByPosition`.
  Публикует сырые сделки и локальный `.proof` с привязкой к счёту, серверу,
  символу и POSITION_IDENTIFIER. Тяжёлая сверка истории по умолчанию вынесена
  из торгового EA: `RequireObserver=true`. Главный EA проверяет свежесть,
  входной order ID, magic, уникальность deal ID и баланс объёмов с текущей
  позицией. Отсутствие позиции само по себе не означает закрытие.
- `ImpulsSLMonitor.mq5` — рекомендации SL, без торговых вызовов. Список позиций
  получает из сохраняемого манифеста главного EA. Достигнутый порог, курсор
  истории тиков и номера рекомендаций сохраняются. Главный EA повторно
  проверяет ticket, SL/TP, объём, вход, котировку и ограничения брокера.
- `tradfi/native_transport.py`, `native_service.py`, `web/native-panel/*` —
  аутентифицированная локальная панель, очередь намерений и существующая
  доставка диагностических логов в Telegram. Python не вычисляет торговую
  стратегию, не импортирует MT5 в native-ветке и не отправляет ордера.

Главный EA и SL-монитор должны находиться на разных графиках **того же
XAUUSD.s**; `_Symbol == TradeSymbol` проверяется. Наблюдателю достаточно таймера.
Все три используют один `MailboxFolder`, один счёт/сервер/символ.

## Исполнение и сохранение

Перед `OrderSend` в полном снимке сохраняется **UNKNOWN**. Ни таймаут, ни
перезапуск не переводят его обратно в READY. Пропавший ответ сверяется по
сохранённому order ID либо уникальному комментарию команды, затем по позициям
и сделкам. При неоднозначности повтор запрещён. Положительный ответ
OrderSend не считается подтверждением исполнения или защиты.

`native-state.txt` содержит все команды, привязки, настройки, финансовые суммы,
паузы и незавершённые общие команды. `native_audit/` сохраняет неизменяемые
редакции состояния и изменённых записей; старые события не удаляются.
Installation ID отдельно привязан к журналу: удаление снимка не разрешает
автоматически создать пустой журнал с прежними ID. Повреждение/расхождение
останавливает владельца, а не восстанавливает операции догадками.

Это **не транзакция с брокером**. FileFlush/FileMove не дают exactly-once с MT5.
После сохранения и непосредственно перед отправкой выполняется ещё одно
чтение SL/TP/объёма. Но API MT5 не имеет compare-and-swap для SL: остаётся
неустранимая гонка с внешним ручным изменением уже после последней проверки.

SL/TP и закрытия адресуются через `request.position = POSITION_TICKET`.
POSITION_IDENTIFIER используется для устойчивой идентичности/истории;
`PositionModify(symbol)` не применяется. Неопределённая операция блокирует
повтор по тому же ресурсу, не новые намерения для других доказанных ресурсов.

CANCEL не требует свежего тика или валидной котировки: удаление pending
ордера проверяется по его ID, символу, magic и ответу/сверке брокера.
При разрыве связи отмена не объявляется выполненной.

STOP, SL/TP и CLOSE **не отклоняются по возрасту котировки**: нет порога
«5 секунд». Запрос принимается и сохраняется; если новый валидный тик не
наблюдался, он остаётся в WAIT_TICK / EA_ACCEPTED с причиной ожидания,
без OrderSend. Следующее наблюдаемое изменение тика освобождает очередь,
после повторной проверки позиции, ручного SL/TP и ограничений брокера.
Один новый тик разрешает всю ранее ожидавшую очередь; отправка ограничена
четырьмя операциями на обработчик, оставшиеся не требуют ещё одного тика.
После разрыва связи разрешения сбрасываются до нового наблюдения.
При холодном запуске таймерный снимок задаёт только базу. Первый реальный
OnTick достаточен, даже если он пришёл до базы или его поля совпадают
с базовым снимком; ждать второго отличающегося тика не требуется.
CANCEL освобождается после связи без ожидания тика; ещё не отправленный
STOP отменяется локально и на следующем тике не появится.
Если pending-ордер исчез до REMOVE, отмена переходит в RECONCILING:
проверяются история, symbol/magic/comment исходной команды и, при
исполнении, связанная позиция/сделки. Отсутствие ордера не считается
отменой или исполнением. Исполнившийся ордер получает отдельный итог
ORDER_FILLED_BEFORE_CANCEL_POSITION_RECONCILED. Недоступная история
оставляет запрос на сверке без повторного REMOVE. Очередь отправки
обходит RECONCILING и использует круговой обход, поэтому начало очереди
не вытесняет её хвост.
UNKNOWN означает, что отправка могла произойти, и никогда не переходит
обратно в очередь из-за таймаута. Высокоуровневый запрос при отсутствии
связи сохраняется с WAITING_CONNECTION_NOT_SENT. Для ценовой веб-команды сохраняется отдельная привязка намерения к
position ID, ticket, корзине, объёму, входу, SL/TP и существенным настройкам.
Посторонняя ревизия журнала не отменяет принятый запрос. Изменение цели
даёт явный DEFERRED_TARGET_CHANGED_OR_UNAVAILABLE без отправки; если
при принятии цель невозможно связать, требуется проверка вместо догадки. Подготовленные WAIT_TICK операции сохраняются
при перезапуске; незавершённые READY-пакеты по-прежнему не воспроизводятся.

Панель сохраняет ID команды до отправки, показывает AWAITING_EA, EA_ACCEPTED,
AWAITING_BROKER и UNKNOWN отдельно от BROKER_CONFIRMED. Независимые команды
принимаются без ожидания фоновой сверки MT5. Настройки получают APPLIED,
которое не выдаётся за брокерское исполнение.

## Стратегия

- Начальный вход — одна позиция **0.02**, исходные SL/TP берутся из явных
  настроек. SL 1.00 нигде не принят за обязательное значение.
- После полного первоначального SL — 3 × 0.01, затем +1 ступень после каждого
  следующего полного SL, **один раз на корзину**. Недонабранная/частично
  исполненная корзина не считается полной для увеличения.
- Уточнение Михаила реализовано: часть ступеней TP, остальные первоначальный
  SL — **сохранить прежний объём**, учесть все фактические результаты.
- Подтверждённый SL поддержки объём не увеличивает. Исходный SL берётся из
  фактической входной сделки, перемещение — из broker readback / DEAL_SL
  закрытия. Одна рекомендация или успешная отправка не меняет классификацию.
- Полный SL 0.10 запрещает автоматическое продолжение. Независимые защитные
  и закрывающие команды остаются доступны. Пользователь выбирает объём
  0.02–0.10 и редактирует профиль, затем отдельной кнопкой подтверждает
  показанные TP, SL, отступ и RECOVERY. EA сверяет профиль с сохранённым,
  проверяет отсутствие незавершённых ресурсов и лишь затем возобновляет
  свечное следование. Повтор команды не создаёт второй вход.
- Начальные и RECOVERY STOP следуют закрытым направленным M1, с **раздельно
  настраиваемыми отступами**. Перед заменой сначала отменяется и сверяется
  старый ордер; его исполнение имеет приоритет над новым входом.
- После SL поддержки начальной 0.02 следующий RECOVERY вход — две позиции
  по 0.01. Подтверждённый профиль 0.02: TP 0.30 / 0.70, редактируемый в
  настройках; последний доступный TP корректируется под фактический RECOVERY.
  Признак двух ступеней и профиль сохраняются при перезапуске.
- Профили 0.02–0.10 утверждены и редактируются. 0.08: 0.70/1.30/2.30/3.30/4.00/4.70/5.10/5.60;
  0.09: 0.70/1.30/2.30/3.30/4.00/4.70/5.50/6.30/6.90;
  0.10: 0.70/1.30/2.30/3.30/4.00/4.70/5.50/6.50/7.50/8.20.
  Сохранённые пользовательские профили не перезаписываются при загрузке;
  удалённый/некорректный профиль блокирует соответствующий новый вход.
- Фактический RECOVERY пересчитывается из всех уникальных сделок позиции:
  profit + commission + swap + fee, включая входные расходы. Повторная сверка
  заменяет наблюдаемую сумму, а не прибавляет её второй раз. Поздние расходы
  закрытых позиций пересматриваются отдельно от очереди активных операций.
- Последний доступный TP выбирается по максимальному исходному индексу
  **ещё открытой** ступени. Цена находится через OrderCalcProfit, с проверкой
  tick/stops/freeze. TP может стать ближе остальных. Для последней ступени
  из фактического долга вычитается ожидаемая чистая прибыль других ещё открытых
  ступеней по их фактическим TP и оставшимся объёмам, добавляется резерв её
  выходных расходов. Пример без расходов: долг 2.00 минус 0.30 и 0.70 → 1.00
  на последнюю. Прогноз используется только для цели TP, не записывается
  как полученная прибыль. Уже закрытые ступени входят только в фактический
  ledger, поэтому второй раз не вычитаются. Если все позиции закрыты, остаток
  сохраняется на следующий вход. Неположительная/недопустимая цель даёт
  видимый статус необходимости решения, прежний TP не заменяется убыточным.
- Установленный пользователем TP сохраняется как ручной выбор. Изменение
  долгозависимой цели не должно затирать его на следующем тике.

## SL и панель

По умолчанию BUY: Bid >= entry + 0.25 → SL = entry − 0.25;
Bid >= entry + 0.40 → SL = entry. SELL зеркально по Ask.
FirstThreshold, SecondThreshold, FirstOffset и SecondOffset настраиваются
в SL-мониторе; это единицы цены, не технические MT5 points.

Монитор сохраняет достигнутый порог при откате/перезапуске. CopyTicksRange
проверяет ограниченные окна после времени входа, чтобы обнаруживать пик,
пропущенный из-за объединённых OnTick. При ошибке/усечении курсор не
продвигается; текущая доступная котировка всё равно проверяется. Это не
обещание восстановить тики, отсутствующие у самого брокера, или дать
абсолютную гарантию реакции во время разрыва связи.

В нативной панели есть M1, линии SL/TP с подтверждением, SL-контроль,
SL на вход, обратная лестница, отдельная отмена триггеров, остановка новых
входов, **«Закрыть все позиции бота»**, профили, закрытые позиции и логи.
Интерфейс native теперь основан на исходном **basket-panel**: сохранены
разметка, CSS, свечной renderer, Bid/Ask, zoom/pan/pinch, удержание линии
0.5 секунды, подтверждение, вкладки, цвета, высота и выгрузка логов. Адаптер
только переводит снимки/команды. Видимая ручная панель MARKET/STOP удалена;
отмена всех триггеров вынесена отдельно. Добавлены закрытие всех и явное
продолжение после 0.10. Сохранены разовая отмена начального триггера,
сверка, сброс паузы и списание RECOVERY. Последнее требует остановки,
отсутствия позиций/pending/UNKNOWN и подтверждения текущего долга;
меняется только база RECOVERY, фактический результат и история сохраняются.

Настройки следующего входа редактируются при действующей корзине. Её
отступ, SL и исходные TP сохраняются отдельным basket-config и не заменяются
новыми настройками даже при свечной перестановке pending-ордера. Выбор
следующего профиля применяется при создании следующей корзины.
В веб-настройках доступны оба порога и оба сдвига SL-монитора. Главный EA
сохраняет их, монитор читает с проверкой счёта/сервера/символа и заново
проверяет достигнутые пороги; старый более выгодный брокерский SL сохраняется.
Рекомендация содержит значения использованных порогов/сдвигов: торговый EA
отвергает запоздавший сигнал со старыми настройками.

Обратная лестница сохраняет прежнюю формулу: нулевой ранг среди оставшихся
позиций, доля rank/count от собственного фактического входа к стороне
закрытия. Нужны TP1 и подтверждённая защита на входе; план не превращается
в бесконечный trailing. Более выгодный SL не ухудшается.

«Закрыть все» — сохраняемая составная команда: отмена своих pending-ордеров,
наблюдение возможного исполнения при отмене, закрытие доказанных позиций,
сверка. Отказ одной части не выдаётся за закрытие всех. Чужие ручные ордера
и позиции не принимаются под управление по одному magic/символу.

## Триггеры на SL

Кнопка реализована: встречная лестница ставится на **фактический общий SL**
открытых позиций исходной корзины. Цена фиксируется в журнале и не следует
ни свечам, ни последующим ручным изменениям SL. Повтор кнопки при уже
сохранённом плане запрещён; UNKNOWN не переотправляется. План встречной
корзины сохраняется отдельно от текущей: исполнение встречного ордера раньше
события закрытия исходной позиции не создаёт вторую лестницу.

Будущий объём рассчитывается по подтверждённому состоянию исходной корзины:
полный первоначальный SL — увеличение, поддержка/предшествующие TP — прежний
объём. Предварительный RECOVERY включает расчёт оставшегося объёма по SL
через OrderCalcProfit и резерв выходных расходов; входные расходы уже входят
в журнал. Последний TP предварительно рассчитывается до отправки. После
сверки закрытия оценка исключается, применяется фактический результат.
Открытая встречная ступень корректируется даже при ещё открытом источнике;
если источник исчез, но история ещё не подтверждена, коррекция ждёт сверки.
Резерв ExitCostReserve — оценка, не утверждение о фактической комиссии.

SL-монитор получает отдельную привязку position → basket, поэтому источник и
встречная корзина одновременно получают рекомендации своего цикла.

**Оставшиеся исключительные сценарии:** если оставшиеся позиции имеют разные
SL, кнопка отклоняется с `SOURCE_SL_LEVELS_DIFFER_REQUIRE_SELECTION`: один
уровень без выбора пользователя не угадывается. Если после постановки
изменился исход (например, ручной перенос превратил первоначальный SL в
поддержку), уже созданная лестница не дублируется и не изменяет объём тайно:
`FIXED_VOLUME_OUTCOME_REQUIRES_REVIEW` приостанавливает новые авто-входы;
существующие позиции сохраняют защиту. Для этих случаев потребуется выбор
владельца. Объёмы ручного продолжения вне диапазона 0.02–0.10 не реализованы.

## Миграция и проверки перед возможной установкой

Основной `tradfi_main.py` понимает `backend=ea_native_v1`, выбирая чистый
панельный сервис до создания MT5Broker/Controller. Старый конфиг не
переписывается. `--execute` Python для native backend отклоняется.
Пример — `native_config.example.json`; имена счёта, путь Common Files,
installation UUID и пароль нужно заполнить реальными согласованными данными.

Для подтверждённого **нового сервера** предусмотрен
`tools/prepare_native_new_installation.py --settings <явные-параметры.json> --destination <новый-каталог>`.
Он не читает старую базу и создаёт новый UUID, review/config с
NewAccountingStart=true, StartingRecovery=0, StartingSteps=2 и выключенной
торговлей. Требуются login/server/symbol/magic/common_files_directory и
положительные InitialSLDistance, InitialTPDistance, CandleOffset,
RecoveryCandleOffset, RecoverySLDistance. Существующий каталог не затирается.

При первом запуске EA фиксирует accounting_start и принимает только новые
команды этого журнала: старые закрытые сделки не включаются в итоги или долг
и не удаляются из MT5. Открытые позиции и pending-ордера целевого символа,
включая чужие, блокируют создание свежего журнала. Диагностический
снимок native-view.json перечисляет их с owned=false, журнал терминала
указывает причину отказа. После отказа OnInit снимок не обновляется:
панель через 5 секунд показывает отсутствие свежей связи, а файл остаётся
для разбора; это не доказательство последующего состояния брокера. Перезапуск с тем же
NewAccountingStart=true **не сбрасывает** уже существующий журнал или долг.
Для нового UUID обязателен отдельный пустой MailboxFolder. Это не обход
неизвестного результата старой установки; активный старый владелец должен
быть остановлен. Вариант переноса старого долга ниже сохранён для других
установок и не выполняется для нового старта Михаила.

`tools/prepare_native_migration.py` **офлайн** создаёт приватную SQLite backup,
копию старого конфига и migration-review.json. Он сохраняет старые профили,
текущий initial TP, SL и отдельные отступы, показывает незавершённые команды,
но не подтверждает состояние брокера и не активирует торговлю. Не публикуйте
его выходной архив: старый конфиг может содержать пароль панели.

Новый журнал создаётся только при подтверждённой миграции, явных положительных
расстояниях и отсутствии позиций/ордеров данного символа. При ненулевом
StartingRecovery требуется явное CarryStageConfirmed и выбор StartingSteps.
Старый долг не списывается, неизвестные операции не переносятся как выполненные.

По умолчанию AllowTrading=false, LegacyOwnerStopped=false,
MigrationConfirmed=false. После перезапуска новые входы остаются на паузе.
Общий Common Files lock предотвращает параллельных native-владельцев;
обновлённый Windows Python executor использует совместимый lock до подключения.
Старая, ещё не обновлённая копия Python не знает этого lock — её остановка
остаётся обязательным условием миграции.

Нативный журнал имеет ограничение 10000 команд; с 9000 прекращаются новые
автоматические входы, оставляя запас для защитных действий. Автоматическая
компактация/удаление аудита не выполняется. Ошибка записи, коллизия редакции
или повреждённый снимок требует восстановления из сохранённых данных,
а не автоматического replay запросов.

## Что проверено и что не проверено

Итоговый полный офлайн-прогон: **1475 тестов, OK**, см. приложенный лог.
`Blocked real network attempts: 0`.

- Полная Python-регрессия запускается через `tools/run_offline_tests.py`
  с запрещёнными сетевыми подключениями. MetaTrader5 не устанавливался.
- Реальный RecoveryPolicy.mqh компилируется через g++ с math-оболочкой.
- Исходники **всех трёх EA** механически адаптируются только для синтаксиса
  MQL-массивов/input и компилируются против детерминированного C++ MT5 mock.
  Стратегия, journal, handlers и executor берутся из фактических исходников,
  а не из отдельной Python-переписи.
- Проверены потерянный OrderSend-ответ, UNKNOWN/restart, отказ журнала,
  недоступная/повторная история, partial fills, поддержка/полный SL,
  смешанные TP/SL, фиксированные триггеры на SL, раннее исполнение встречной
  позиции, замена предварительного долга фактическим, ручное продолжение
  после 0.10, новая точка учёта без удаления истории, последний TP закрыт раньше других, перенос остатка,
  ручной TP, разные POSITION_IDENTIFIER и ticket, отказ одной позиции,
  поздняя рекомендация SL, ручное улучшение во время OrderCheck,
  объединённые тики и неисправная история тиков, длительная пауза котировок, один новый тик,
  отмена unsent STOP, потеря связи между подготовкой и отправкой,
  сохранение WAIT_TICK при перезапуске, снимок EA → JSON панели,
  аутентификация и отсутствие торгового API в новом Python runtime.
- JavaScript проверен `node --check`; JSDOM выполняет фактические скрипты
  панели на моках: свечи/Bid/Ask, zoom, независимые команды, сохранение
  порогов SL и наличие прежних кнопок. Chromium/Playwright smoke подготовлен,
  но запуск Chromium заблокирован системным запретом socket(): браузерная
  проверка жестов и визуального UX **не прошла запуск**, не считается успехом.
  Windows lock с реальным терминалом здесь не испытан.
- **MetaEditor, Wine и PowerShell отсутствуют.** C++ mock-компиляция не
  является MQL5-компиляцией. `tools/compile_native_mt5.ps1` подготовлен для
  отдельной проверки MetaEditor, без установки EA/запуска терминала; здесь
  он не запускался. `.ex5` не предоставляются как якобы проверенные.

На реальном брокере остаются непроверенными build-specific MQL API,
stop/freeze/filling условия XAUUSD.s, задержки/корректировки его истории,
поведение файловых блокировок и непрерывная работа. Успешные моки не
доказывают готовность к реальным деньгам. Ни одной реальной сделки нет.
