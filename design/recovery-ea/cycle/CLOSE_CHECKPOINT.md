# Чекпоинт закрытия RECOVERY

`RecoveryCloseCheckpoint.mqh` хранит подтверждённый закрытый вход и момент
перехода диапазона в одном неизменяемом локальном файле. Запись включает
привязку операции, точные тикет и идентификатор, предыдущее состояние,
подтверждённый тип закрытия и дистанцию переоткрытия. Новый счётчик и план
вычисляются из записи тем же `RCApplyClose`, без самостоятельной отправки
каких-либо ордеров.

1. `RCCPStageFromWire` получает полное, привязанное подтверждение от обоих
   читателей. Неполная история, ненулевой остаток, спорная причина и ещё
   не определённый переход по TP не производят чекпоинта.
2. Исполнитель назначает уникальный *сохранённый* ID операции и создаёт запись
   через `RCCPPublish`. Публикация не заменяет существующую запись. При сбое
   не создавать новый ID взамен: сверить файл прежнего ID. Прочитать назад
   через `RCCPRead` с исходным ключом и сравнить полную каноническую запись.
3. `RCCPApply` изменяет диапазон только если текущее состояние точно равно
   записанному состоянию до перехода. Повтор при точно совпадающем конечном
   состоянии не меняет счётчик и не выдаёт второе намерение; произвольное
   несовпадение отправляется на сверку. Отдельный журнал исполнения решает,
   был ли уже передан следующий план, и никогда не выводит это из этого файла.

Нет проверки возраста котировок и нет новых галочек. Корень доверия здесь
уже проверенный локальный журнал под управлением единственного исполнителя;
файл не подписан и не может доказывать данные брокера сам по себе.
Строгий формат проверяет полноту и структуру, а не подлинность данных.
Замена или потеря локального журнала требует сверки, а не повторной отправки.
Поведение FileFlush/FileMove и восстановление после аварийного завершения
пока не проверены в терминале или на VPS.

Хост-тест из корня репозитория:
```sh
python3 design/recovery-ea/cycle/test_close_checkpoint_compat.py
```
