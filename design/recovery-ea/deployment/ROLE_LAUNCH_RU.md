# Подготовка трёх графиков RECOVERY на чистом терминале

План запуска использует одну локальную установку MT5. Не запускать
торговый советник и не включать Algo Trading при подготовке и диагностике.
`role_launch.py` лишь вычисляет структуру входов по явно заданному профилю.
Сеть, терминал, очередь, старые файлы и торговые операции он не затрагивает.

1. Берём канонический ID текущей установки из нового приватного профиля
   (тот же ID будет ожидать веб-канал), точные номер счёта, сервер, символ
   MT5 и выбранный идентификатор стратегии. Не использовать счёт/символ из
   предыдущей установки по умолчанию. Подготовить новый `RoleLaunch` на
   этот запуск через `prepare_role_launch`. Случайный `instance_seed`
   нужен один раз; его не копируют между запусками.
2. На двух разных графиках выбранного символа одного терминала
   `RecoveryVerifier` и `RecoveryPriceWatcher` получают свои наборы входов
   `verifier_inputs()` / `watcher_inputs()`. У обеих ролей одинаковый
   `ExecutorEpoch`, но разные собственные идентификаторы. Точные
   `ChartID()` двух графиков видны в строках готовности каждой роли в
   журнале Experts. Одна строка подтверждает инициализацию наблюдателя,
   но не торговую готовность и не прохождение обмена.
3. Для будущего основного советника на **третьем** графике передать
   результат `owner_binding(owner_chart=..., verifier_chart=...,
   watcher_chart=...)` управляющему коду. Он обязан включить свои
   проверки счёта/символа и не подставлять готовность по одной строке журнала.
   `owner_binding` проверяет различие ID, но не общается с терминалом.
   Полноценной точки входа основного EA в проверенном срезе ещё нет.
4. При новом запуске всех ролей заново выбрать входы одной свежей серии;
   не пытаться использовать прошлые epoch, chart ID, командные квитанции
   или открытые заявки как сохранённое состояние. Не привязывать epoch к
   часам телефона, сервера или сроку годности. Сам перезапуск никак не
   отменяет существующие заявки на стороне брокера.

## Совпадение с MQL5

Значение для поля `ExecutorEpoch` получается из первых 32 шестнадцатеричных
знаков SHA-256 байтов UTF-8 строки
`RECOVERY_LIVE_SESSION_V1<TAB>boot<TAB>profile_scope:instance_seed`. Это
`RecoveryLiveUuid("boot", …)` без дефисов (`RecoveryPanelBootEpoch`).
Собственные идентификаторы свидетелей задаются через раздельные домены
`verifier` и `watcher` с тем же случайным материалом. Они не являются ключами
веб-панели. Ключ панели и брокерский пароль в эти входы не входят.

Для поставки без ручного копирования можно сделать дополнительный
одноразовый обмен: читатели публикуют ID своих графиков для свежего
`ExecutorEpoch`, основной советник сверяет учётные признаки и проверяет
ответ конкретного наблюдателя прежде, чем объявить новый почтовый ящик
готовым. Старые регистрации игнорируются по другому epoch, не по времени.
Такой обмен потребует адаптации обоих EA; Python-планер сам его не делает.
Не считать имеющийся `RecoveryPairProbe` способом проверки на реальном
счёте: исходник прямо ограничен демо-счётом. Демо и реальные заявки здесь
не запускались.

Офлайн-проверка в этой папке: `python -m unittest -v test_role_launch`.
