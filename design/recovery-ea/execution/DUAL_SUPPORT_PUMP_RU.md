# Сверка исполнения одного из двух точных ордеров

Для пары после закрытия по SL поддержки владелец замораживает уже известные
тикеты: повторный вход и старый встречный STOP. Он выделяет четыре разных
nonce для двух точных запросов, истории и снимка и отдельный тег публикации;
все запросы относятся к одной эпохе сверщика и текущему сеансу. При
`RecoveryBeginDualSupport` исторические anchor_order и position_identifier
нулевые: автомат получает их только из связанного точного подтверждения.

`RecoveryStepDualSupport` действует по одному шагу из таймера. Локальная
проверка одного исторического FILLED лишь запускает независимую сверку.
Положительный результат требует одного точного FILLED и одного точного
неизменённого PLACED, истории сделок исполнившегося тикета и полного
последующего снимка его фактической позиции и оставшегося ордера. Для
`RDS_PROOF` возвращаются `RRFilled` и точный `RRKnownOrder` уцелевшего
ордера; `verified_sequence` содержит номер последнего снимка для будущей
сверки изменения. Только после этого владелец может готовить перенос
цены уцелевшего тикета. При двух независимых FILLED возвращается
`RDS_COLLISION` без выбора стороны. Если второй отчёт ещё PLACED, но
позднее в снимке он уже отсутствует, результат UNKNOWN, а не выдуманное
исполнение. Абсолютной атомарности между снимками нет, поэтому шлюз
изменения повторно сверяет собственный точный тикет.

При быстром исполнении повторного входа до подтверждения PLACED
`RecoveryDualPendingReentryView` создаёт лишь копию для опроса из
точных key/ticket текущего RAM-журнала и неизменяемого RR_REENTRY.
Копию нельзя принимать за живое состояние. После `RDS_PROOF`
`RecoveryDualPendingReentryEffect` разрешает владельцу подтвердить этот
RR_REENTRY и подготовить ротацию в одной операции над состоянием.
Отсутствие записи, смена цели, частичный или неясный результат не
создают доказательство и не заставляют отправлять заявку повторно.
Автомат ничего не отправляет брокеру, не закрывает позицию, не
восстанавливает прежний сеанс и не выбирает ордер по цене.

`python execution/test_dual_support_compat.py -v` проверяет обе стороны,
коллизию, пропажу уцелевшего ордера и быстрый вход через журнал, с
имитацией терминальных вызовов. MetaEditor/MT5 не запускались.
